## Global Rules
- All `/api/v1/admin/*` endpoints require HR authentication (cookie/token).
- All list endpoints MUST include `page` and `limit` query parameters (Rule 13.2).
- **Scope (local-only):** The app runs only at `10.0.10.37:8000` on the LAN. The apply wizard is hosted in `bte_webapp` (`/apply`). Cross-app work with `bigtimeempire.com` is paused, except for job postings (next rule).
- **Job postings (decided 2026-10-14, user):** A job's Title, Description and Requirements are the public job posting, shown on the local website (container `bte-website`, `http://10.0.10.37:8086/careers`). The posting has an "apply here" button that opens the job's designated form (`jobs.form_id`). The form, not the job, holds the pass/fail thresholds (to be set up later). Jobs use the same slug and id format as brands and forms: uuid id, slug generated server-side from the title, page URLs carry the id. This lifts the cross-app pause for job postings only; nothing else for `bte_website` is in scope. NOT decided yet, so no endpoint is contracted by this rule: the create, list and public posting endpoints, and how the website reaches the API (CORS for exactly `http://10.0.10.37:8086`, or an nginx proxy route on the website side). See PROJECT_STATE.md OPEN Decisions.
- **Timestamps (decided 2026-10-14, user):** Timestamps are stored in UTC (`timestamptz`, unchanged) and returned in Philippine Time (PHT, Asia/Manila, UTC+08:00) as ISO 8601 with the offset, e.g. `2026-10-14T11:16:23+08:00`. This applies to every timestamp field in every response (`created_at`, `archived_at`, the duplicate-application `date`, and any new ones); fields shown as `"timestamp"` in this document follow this rule. The timezone comes from one configured value, never written inline in endpoint code. Implemented so far only in `POST /api/v1/admin/brands/{brand_id}/jobs` and `GET /api/v1/admin/brands/{brand_id}/jobs` (via `app/timeutil.py`, verified live 2026-10-14); every other endpoint still returns UTC until it is converted, one endpoint at a time.
- **Sidebar rule (decided 2026-10-14):** The existing admin sidebar (`app/templates/_sidebar.html`, filled by `app/static/admin-sidebar.js` from `GET /api/v1/admin/metadata/sidebar`) is the ONLY admin sidebar and is the default for every admin page. It never changes structurally -- only its contents change (brand and form lists). Never create, propose or ask about a different or second sidebar; new admin pages include the shared `_sidebar.html`.

### `POST /api/v1/public/apply`
- **Purpose:** Submit an application.
- **Flow (DECIDED 2026-10-15, NOT implemented):** two-step apply UI, single final submit. Step 1 (client-side only, no backend call) collects the fixed personal-data fields below; its "Proceed with questions" button advances to step 2 without submitting anything to the server. Step 2 is the existing one-question-at-a-time wizard, driven by `GET /api/v1/public/jobs/{job_id}/questions`. Only after step 2's last question is answered does the client send ONE `POST` here with everything from both steps together.
- **Content-Type:** `multipart/form-data`
- **Request:**
  * `job_id` (uuid)
  * `first_name`, `last_name`, `email`, `phone`, `address`, `gender`, `date_of_birth` (strings; `date_of_birth` as `YYYY-MM-DD`, must be a real past date, else 422) -- fixed, required request fields for every job, collected on step 1 of the apply flow (DECIDED 2026-10-15, NOT implemented). This SUPERSEDES the field_key design immediately below: `job_questions.field_key` is RETIRED for collecting these three fields.
  * `answers` (JSON string array: `[{"question_id": "uuid", "answer": "string"}]`). Every question whose `is_required` is true must be answered, and an answer that is empty after trimming counts as missing (PROPOSED 2026-10-14, NOT implemented; the earlier rule was every YES_NO and MULTIPLE_CHOICE question, which is now the default `is_required` for those types). For MULTIPLE_CHOICE, `answer` is the chosen option's `id` (from that question's `options` list), not its text or a letter. Missing answers, unknown question ids, an unknown option id, or invalid JSON return 422. A job with no form returns 409, and so does a job whose form has a NULL `pass_threshold` or `pooling_threshold` (PROPOSED 2026-10-15, default pending Structure confirmation). The job and form are validated BEFORE the resume is written to disk. Scoring and suggested fit follow section 3.
  * `resume` (File, PDF only)
  * `terms_version` (string)
  * `consent_agreed` (boolean) - Philippine Data Privacy Act (RA 10173)
- **Response (201 Created):** `{ "message": "Application submitted successfully", "application_id": "uuid" }`
- **Fit rows (PROPOSED 2026-10-15, NOT implemented):** the response never shows the applicant a score or a fit. In the same transaction as the application, the server also writes any `application_fits` rows (see Scoring and suggested fit).
- **Status (code review 2026-10-14, not run live):** `submit_application` in `app/routers/public.py` does NOT yet follow this contract. It queries questions by `job_id`, compares answers to `expected_answer`, does not return 422 for missing answers or 409 for a job with no form, and reuses an existing applicant by email without updating it. The apply rewrite is the first code step (Structure handoff, option B approved by the user 2026-10-14); `is_required` comes after it. `field_key` is RETIRED (2026-10-15, see Flow note above) -- address/gender/date_of_birth are fixed request fields, not form questions, so `field_key` is no longer part of this endpoint's design.

### `POST /api/v1/admin/brands`
- **Purpose:** Create a brand from the sidebar BRANDS "+" Add brand modal. Contract decided 2026-10-14; backend implemented and verified live 2026-10-14 (`app/routers/admin.py`): 201 create, 409 duplicate, 422 blank or symbols-only. ### `POST /api/v1/admin/brands/{brand_id}/jobs`
- **Purpose:** Create a job under a brand from the "+ Create Job" modal (decided 2026-10-14, user). Title, Description and Requirements are the public job posting.
- **Request:** `{ "title": "string", "description": "string or null", "requirements": "string or null", "is_active": bool }`. `title` is required and must contain at least one letter or number (same rule as brand names). `is_active` defaults to `false`.
- **Publish state (decided 2026-10-14, user, option B):** the state lives in `jobs.is_active`, with no separate column. The modal's dropdown sends: Publish = `true`; Save as draft = `false`. Draft and Unpublished are stored the same way (both `false`). The public board shows only `is_active = true` jobs.

### `POST /api/v1/admin/forms/{form_id}/questions`
- **Purpose:** Add a question with its answer points. `display_order` is assigned server-side as last + 1.
- **Request:** JSON `{ "question_type": "YES_NO|MULTIPLE_CHOICE|OPEN_ENDED", "question_text": "string", "options": ["Choice text 1", "Choice text 2", "Choice text 3"], "is_hard_requirement": bool, "is_required": bool (optional), "answer_points": [ { "answer_value": "<option id>", "target_type": "FAIL", "job_id": "uuid" } ] }` (for MULTIPLE_CHOICE, the create request sends plain option text; the server assigns a stable `id` to each option and returns it in the response. `answer_points` for MULTIPLE_CHOICE uses that server-assigned `id`, never text or a letter -- so answer_points can only reference MULTIPLE_CHOICE options on a follow-up PATCH once the create response's ids are known.)
- **Rules:**
  * `YES_NO`: optional `options` of exactly 2 non-empty, distinct label texts (e.g. ["Own a car", "Do not own a car"]). `options[0]` is the display label for `YES`, `options[1]` for `NO`; omitted or null means the labels Yes / No. `answer_value` is always "YES" or "NO" and scoring is unchanged (implemented 2026-10-13 in POST and PATCH questions).
  * `MULTIPLE_CHOICE`: at least 3 `options` (no maximum), each trimmed, non-empty, and distinct (case-insensitive). On create, the server generates a stable `id` for each option; `answer_value` in `answer_points` is that `id`, never text or a letter. On PATCH, an option object that includes an existing `id` keeps that id (and can have its `text` edited); an option object with no `id` is treated as new and gets one assigned; an existing `id` left out of the submitted list is deleted along with any `answer_points` rows that reference it.
  * `OPEN_ENDED`: no `options`, no `answer_points`, `is_hard_requirement` must be false.
  * `is_required` (PROPOSED 2026-10-14, NOT implemented): optional boolean. Omitted means true for `YES_NO` and `MULTIPLE_CHOICE` and false for `OPEN_ENDED`. `is_hard_requirement` true requires `is_required` true (else 422). On apply, an unanswered optional YES_NO or MULTIPLE_CHOICE question is excluded from the score divisor and cannot fail the applicant.
  * `field_key` (RETIRED 2026-10-15: address, gender and date_of_birth are fixed apply fields, see `POST /api/v1/public/apply`; the text that follows is the old design and is NOT to be built): optional, one of `address`, `gender`, `date_of_birth`, allowed only on `OPEN_ENDED` (so no `options`, no `answer_points`, `is_hard_requirement` false). At most one question per `field_key` per form (409 if it already exists). It cannot be changed after create. A question with a `field_key` is never scored. Needs a migration for `job_questions.field_key` and `job_questions.is_required`, plus `applicants.address`, `applicants.gender` and `applicants.date_of_birth` (see SCHEMA.md).
  * `target_type` is `FAIL`, and every row needs a `job_id` of an existing job that uses this form (else 422). Pass/fail is set PER JOB (PROPOSED 2026-10-15, NOT implemented): the BRAND target, `brand_id` and `points` are dropped from the design (see SCHEMA.md). At most one row per answer and job (a duplicate returns 422).
  * One answer choice may have several rows, one per job it fails (for example fails Cashier but passes Store Supervisor).
  * `is_hard_requirement` true requires at least one FAIL row on the question (for at least one job). Hard requirements are non-negotiable: a FAIL on this question for a job fails that job outright and keeps it out of the suggested fit (decided 2026-10-15). In the Form Builder it is marked with a toggle next to Required: turning it on turns Required on and locks it, and it is offered only on YES_NO and MULTIPLE_CHOICE questions (PROPOSED 2026-10-15, NOT built).
  * `answer_points` is OPTIONAL for `YES_NO` and `MULTIPLE_CHOICE` (decided 2026-10-13): omitted or an empty list stores no rows, and `is_hard_requirement` is then false. This is how the Form Builder's first Save stores questions, before an answer-points editor exists.
  * Consequence (follows from the scoring rule in docs/SCHEMA.md): a question with no answer_points rows has no FAIL row on any choice, so every answer passes it. It never fails an applicant until FAIL rows are added with PATCH.
  * Storage: the row is created with `form_id` set and `job_id`, `parameter_id` and `expected_answer` NULL (columns relaxed by migration 004, applied 2026-10-13).
  * Interim limit (decided 2026-10-13): until the `answer_points` table exists, a non-empty `answer_points` list returns 422 ("answer points are not supported yet"), and `is_hard_requirement` true returns 422 (it needs a FAIL row). Both lift when the answer_points migration lands.
  * Validation: `question_text` is trimmed and must be non-empty. `question_type` must be one of the three values. Option labels are trimmed and must be non-empty. For `YES_NO`, `options` is omitted/null or exactly 2 labels (an empty list is 422), and the two labels must differ case-insensitively (UNVERIFIED assumption, matches the Form Builder). Stored `options` is null when omitted.
  * `display_order` is max + 1 for the form, so the first question gets 1 (verified live 2026-10-13).
  * Status: Implemented 2026-10-13 (`app/routers/admin.py`, `create_question`; schemas `QuestionCreateRequest` and `QuestionResponse` in `app/schemas.py`; migration 004). Verified live: 201 for YES_NO with default labels (`options` stored as SQL NULL, after the `none_as_null` fix on the model) and with custom labels, `display_order` 1 then 2; 422 for labels equal ignoring case, one label, blank text, unknown type, non-empty `answer_points`, `is_hard_requirement` true, MULTIPLE_CHOICE with 2 options, malformed form id; 404 unknown form id; 409 archived form. OPEN_ENDED create verified in the browser 2026-10-13 (Form Builder Save). NOT tested: MULTIPLE_CHOICE success path, an empty option label, an empty `options` list on YES_NO. Call site: `app/static/admin-sidebar.js` (Form Builder Save: creates the form, then posts each Yes / No card in order with its name and two labels as `options`; wired 2026-10-13; verified in the browser 2026-10-13: the form is created, then its Yes / No question is stored with its labels, confirmed in `job_questions`). NOT tested: the partial-failure path (form created but a question fails, then Save retried). Other element types (Multiple Choice) block Save until they have contracts. No HR-auth check yet (existing gap; Security owns it). Known limit: `display_order` is max + 1 with no unique constraint, so two simultaneous saves to one form could share a number.
- **Response (201 Created):** the created question object (same shape as in form detail); `answer_points` is `[]` for now.
- **Errors:** 404 form not found; 409 the form is archived and read-only (same rule as rename, added 2026-10-13); 422 malformed `form_id`, rule violation, or one of the interim limits above.

Edit on a loaded Open ended card sends `question_text` only, no `options` (added 2026-10-13; verified in the browser 2026-10-13: a saved Open ended question was renamed and the new name persisted on reopen; first live OPEN_ENDED PATCH).

### `DELETE /api/v1/admin/forms/{form_id}/questions/{question_id}`
- **Purpose:** Delete a question and its answer points.
- **Response:** 204 No Content.
- **Errors:** 409 if the question already has applicant answers.
- **Status:** Implemented 2026-10-13 (`app/routers/admin.py`, `delete_question`). Note: no archived-form check on this endpoint (unlike POST/PATCH) -- the contract's Errors list for DELETE never specified one, so none was added; flagged for confirmation. Verified live: 404 unknown question id. 204 success path verified in the browser 2026-10-15 (element deleted, stayed gone after reopening the form, and the change showed on the apply form, which reads the same questions via `jobs.form_id`). Call site: `app/static/admin-sidebar.js` (Form Builder, Delete on a saved element card opens `#deleteElementModal`; its Delete button sends the request; 204 or 404 removes the card, 409 shows "Applicants have already answered this element" in the dialog). Unsaved cards in a new form are removed locally with no API call. NOT tested: the 409 path (no applicant answers exist yet) and the network-failure message.

### `POST /api/v1/admin/forms/{form_id}/questions/reorder`
- **Purpose:** Set the question order. The body must list every question id of this form exactly once.
- **Request:** JSON `{ "ordered_ids": ["uuid"] }`
- **Response (200 OK):** `{ "message": "Order updated" }`
- **Errors:** 422 if ids are missing, duplicated or from another form.

### Form submissions (no new endpoint)
A form's submissions are the applications for the jobs that use it: `GET /api/v1/admin/applications?form_id={form.id}` (section 2).

### Scoring and suggested fit (applies to `POST /api/v1/public/apply`)
- Answer values: `YES_NO` is "YES" or "NO", `MULTIPLE_CHOICE` is the chosen option's `id` (a string), `OPEN_ENDED` is the applicant's full free text, stored as is and never scored.
- Score: percent of scored questions (YES_NO and MULTIPLE_CHOICE) whose chosen answer has no FAIL row for the job applied to (job-level scoring, PROPOSED 2026-10-15, NOT implemented). OPEN_ENDED is excluded from the divisor, and so is (PROPOSED 2026-10-14, NOT implemented) any unanswered optional question. (The earlier field_key exclusion no longer applies: field_key is RETIRED as of 2026-10-15, see `POST /api/v1/public/apply`.) A hard-requirement question whose chosen answer has a FAIL row for the job applied to sets `has_hard_fail_flag` and status FAILED. The form's `pass_threshold` and `pooling_threshold` decide the status for every job that uses the form (PROPOSED 2026-10-15, NOT implemented; today the code reads the job's own thresholds).
- Suggested fit (PROPOSED 2026-10-15, replaces the brand-level fit, NOT implemented): at submit, the same answers are scored once for every other job that uses the same form and has at least one `answer_points` row. A job is stored as a fit only if its score is higher than the job applied to AND the answers hit no hard fail for it (a hard-requirement question whose chosen answer has a FAIL row for that job; hard-requirement questions are non-negotiable, decided 2026-10-15). A job the applicant hard-fails is never stored or shown as a fit. Each stored fit is an `application_fits` row (application, job, score), written in the same transaction as the application and never recomputed. The admin sees it as, for example, 76/100 on Store Supervisor and 80/100 on Operations Manager. The flag only informs: it never changes the score or status. Only jobs on the applicant's own form are compared. How the admin endpoints expose the fits (`GET /api/v1/admin/applications/{application_id}` and the job cards) is NOT decided yet and must be contracted before it is wired.
