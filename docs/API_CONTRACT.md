### `GET /api/v1/admin/me`
- **Purpose:** Returns the signed-in admin's details for the profile pill fixed at the bottom of the sidebar on every admin page (moved from the `/admin/home` profile card 2026-11-07).
- **Status:** IMPLEMENTED and VERIFIED LIVE 2026-10-30 (`app/routers/auth.py`, `get_current_user` and `me`; `MeResponse` in `app/schemas.py`): 401 `Not authenticated.` with no cookie and with a bogus cookie (curl); 200 in the browser while signed in as SUPERADMIN, returning exactly `full_name`, `email` and `role`. NOT tested: an expired session row, a deactivated user, a null `full_name` (code review only).
- **Request:** No parameters. The user is identified from the `session_id` cookie.
- **Response (200 OK):** `{ "full_name": "string or null", "email": "string", "role": "SUPERADMIN" | "MANAGER" | "RECRUITER" }`. Never returns `password_hash`, the user id or the session id. Sends `Cache-Control: no-store`.
- **Response (401):** `{"detail": "Not authenticated."}` when the cookie is missing, no `sessions` row matches, `expires_at` has passed, or the user is deactivated (`is_active` false).
- **Auth check:** one reusable "current user" check in `app/routers/auth.py` (cookie, then `sessions` by primary key, then `users` by primary key). Two primary-key lookups, so no new index. Not a list endpoint, so Rules 13.2 and 18.2 do not apply.
- **Not in this contract:** the 10-minute idle timeout and `last_active_at` updates, and applying the check to the other `/admin/*` routes (separate Security step, the known auth gap).
- **Schema dependency:** `users.full_name` (SCHEMA.md section 6, migration 016, APPLIED and VERIFIED LIVE 2026-10-30).
- **Call site (MOVED 2026-11-07 from the `/admin/home` profile card to `initProfilePill()` in `app/static/admin-sidebar.js`; markup in `app/templates/_sidebar.html`, styles in `app/static/admin-sidebar.css`):** the profile pill, a footer at the bottom of the sidebar column on every admin page, fetches this endpoint on every page load and fills initials, name and role. ### `POST /api/v1/admin/change-password`
- **Purpose:** Sets a new password for an account that must change its temporary password (newly added user, or reset by an admin). Stateless, no session needed (CONTRACTED 2026-11-06, user, SECURITY.md section 2 option B and mechanism A). NOT gated by `/admin/*` auth, so it must be explicitly exempt when the auth dependency is checked.
- **Request:** `{ "email": "string", "temporary_password": "string", "new_password": "string" }` (`email` validated as `EmailStr`).
- **Response (204 No Content):** password changed. No cookie is set and no session is created; the user then signs in normally at `/login` with the new password.
- **Response (401):** `{"detail": "Invalid email or password."}` for an unknown email, a deactivated account, a wrong temporary password, and an account whose `must_change_password` is false (flagged accounts only, DECIDED 2026-11-06, user). Same generic message, same dummy bcrypt verify on an unknown email for timing parity. Each 401 counts as a failed attempt in the shared login failure limiter.
- **Response (422):** malformed or missing fields, or `new_password` breaking the rules: 8 to 72 bytes (UTF-8 byte length, never truncated), at least 1 uppercase letter, 1 lowercase letter, 1 number and 1 special character, and different from `temporary_password`. Detail is ONE string listing every unmet rule (DECIDED 2026-11-06, user, option B): `New password must <phrases>.` The phrases, in this order: `be 8 to 72 bytes long`, `include an uppercase letter`, `include a lowercase letter`, `include a number`, `include a special character`, `be different from the temporary password`; with two or more unmet they are joined by commas and a final "and". Malformed or missing fields (including an invalid `email`) get the framework's own 422, shape not checked for this endpoint. The 72-byte cap is our own rule: installed bcrypt 4.0.1 with passlib 1.7.4 silently truncates longer input instead of raising (ASCII-tested 2026-11-06), so a longer `temporary_password` gives a 401, not a 500. ASSUMPTION, UNCONFIRMED: "special character" means any character that is not a letter, number or whitespace. Rules are checked only after the credentials verify, so a 422 never confirms a guess at the temporary password for a wrong one.
- **Response (429):** `{"detail": "Too many login attempts from this IP. Please try again later."}`, the same limiter as login (5 failed attempts per IP per 60s, shared `LOGIN_RATE_LIMIT_CACHE`).
- **Side effects:** `users.password_hash` = bcrypt (same `pwd_context` as login) of `new_password`; `users.must_change_password` = false; in the same transaction, any existing `sessions` rows for the user are deleted. `last_login_at` is not updated. Assumption, UNCONFIRMED: deleting the user's sessions is safe because a flagged user has none issued after this feature lands.
- **Schema dependency:** `users.password_hash`, `must_change_password` (migration 018, APPLIED and VERIFIED LIVE 2026-11-05) and `sessions.user_id`. No schema change.
- **Status:** IMPLEMENTED 2026-11-06 in `app/routers/auth.py` (`change_password`), rules in `app/password_rules.py` (`validate_new_password`), request model `ChangePasswordRequest` in `app/schemas.py`; commit 680a722. Curl-tested on a flagged RECRUITER test account: 401 for an unknown email and a wrong temporary password, 422 for weak and unchanged passwords, 204 with 0 Set-Cookie headers on success, then login 200 with the new password and 401 with the old temporary one, 401 on an unflagged account, 429 from the shared limiter. DB-checked: `must_change_password` false, `last_login_at` moved only at the later sign-in. NOT runtime-tested: sessions deletion on success (code reading only), an inactive flagged account, limiter exclusion of the 422 (code reading only), multi-byte passwords through the endpoint, the framework 422 shape. Call site: the `/change-password` page (shell built, wiring not built); `login.html` still does not handle the login 403.

### `POST /api/v1/admin/mrf/forms/{form_id}/questions`
- **Body:** `{ "question_type", "question_text", "options", "is_required"?, "is_classification"? }`. Job-form rules for options. `is_required` defaults to true for YES_NO and MULTIPLE_CHOICE and false for OPEN_ENDED. `is_classification` is allowed only on MULTIPLE_CHOICE with exactly the three fixed options (Rank and File, Supervisory, Managerial, from app/mrf_lists.py); the question is then required. A second classification question on the same form returns 409 (partial unique index on `form_id` where `is_classification`). A new question goes to the end of the order.
- **Status:** DECIDED 2026-11-12, NOT built.

### `PATCH /api/v1/admin/mrf/forms/{form_id}/questions/{question_id}`
- **Body:** any of `question_text`, `options`, `is_required`. `question_type` is immutable. A classification question's options and flag are locked. MULTIPLE_CHOICE options keep their ids. Question text stays editable on a question that has answers.
- **Status:** DECIDED 2026-11-12, NOT built.

### `DELETE /api/v1/admin/mrf/forms/{form_id}/questions/{question_id}`
- **Response:** 204. The 409 for a question that already has answers arrives with the migration that creates `mrf_request_answers` (no answers can exist before it).
- **Status:** DECIDED 2026-11-12, NOT built.

### `POST /api/v1/admin/mrf/forms/{form_id}/questions/reorder`
- **Body:** `{ "ordered_ids" }`: every question id of the form exactly once, otherwise 422.
- **Status:** DECIDED 2026-11-12, NOT built.
