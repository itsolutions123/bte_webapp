## Authentication

### `GET /api/v1/admin/me`
- **Purpose:** Returns the signed-in admin's details for the profile card on `/admin/home`.
- **Status:** IMPLEMENTED and VERIFIED LIVE 2026-10-30 (`app/routers/auth.py`, `get_current_user` and `me`; `MeResponse` in `app/schemas.py`): 401 `Not authenticated.` with no cookie and with a bogus cookie (curl); 200 in the browser while signed in as SUPERADMIN, returning exactly `full_name`, `email` and `role`. NOT tested: an expired session row, a deactivated user, a null `full_name` (code review only).
- **Request:** No parameters. The user is identified from the `session_id` cookie.
- **Response (200 OK):** `{ "full_name": "string or null", "email": "string", "role": "SUPERADMIN" | "MANAGER" | "RECRUITER" }`. Never returns `password_hash`, the user id or the session id. Sends `Cache-Control: no-store`.
- **Response (401):** `{"detail": "Not authenticated."}` when the cookie is missing, no `sessions` row matches, `expires_at` has passed, or the user is deactivated (`is_active` false).
- **Auth check:** one reusable "current user" check in `app/routers/auth.py` (cookie, then `sessions` by primary key, then `users` by primary key). Two primary-key lookups, so no new index. Not a list endpoint, so Rules 13.2 and 18.2 do not apply.
- **Not in this contract:** the 10-minute idle timeout and `last_active_at` updates, and applying the check to the other `/admin/*` routes (separate Security step, the known auth gap).
- **Schema dependency:** `users.full_name` (SCHEMA.md section 6, migration 016, APPLIED and VERIFIED LIVE 2026-10-30).
- **Call site (WIRED 2026-10-30 in `app/templates/admin.html`, fetched on the first open of the card, VERIFIED in the browser 2026-10-30: initials, name, email and role shown for the signed-in SUPERADMIN):** the profile card in `app/templates/admin.html` (opened by the PROFILE button) fills initials, name, email and role from this response. Initials are the first letters of the first and last words of `full_name`; if `full_name` is null the name line is hidden and the initials circle shows the first letter of the email. Values are rendered as text, never as HTML.

### `POST /api/v1/admin/logout`
- **Purpose:** Ends the current admin session (the LOG OUT button in the profile card on `/admin/home`).
- **Status:** IMPLEMENTED 2026-10-30 (`logout` in `app/routers/auth.py`). VERIFIED LIVE: curl with no cookie and with a bogus cookie both return 204 with `Cache-Control: no-store` and a `Set-Cookie` clearing `session_id` (`Max-Age=0`, `Path=/`, HttpOnly, SameSite=lax); the LOG OUT button was confirmed working in the browser by the user. NOT tested: that the `sessions` row is deleted (DB check), that `GET /api/v1/admin/me` returns 401 afterwards, the button's error path.
- **Auth:** None required. It deliberately does not use `get_current_user`, so a person with an expired or unknown session can still log out and get the cookie cleared.
- **Request:** No body. Reads the `session_id` cookie.
- **Server action:** if the cookie is present, deletes that one `sessions` row by primary key and commits. Only the current session ends, not the user's other sessions. A missing cookie or an unknown session id deletes nothing.
- **Cookie:** always cleared in the response with the same attributes login set: name `session_id`, `Path=/`, HttpOnly, SameSite=Lax, Secure off (LAN HTTP, SECURITY.md section 2).
- **Response (204 No Content):** every time, including with no cookie or a bogus one (idempotent, reveals nothing about session validity). Sends `Cache-Control: no-store`. Only an unexpected server failure returns 500.
- **Why POST:** it changes state; a GET could be triggered cross-site. Not a list endpoint, so Rules 13.2 and 18.2 do not apply; one primary-key delete, no new index.
- **Call site (WIRED 2026-10-30 in `app/templates/admin.html`, button confirmed working in the browser by the user):** the LOG OUT button (`id="profile-logout"` in `app/templates/admin.html`) sends the POST, disables itself while the request runs, then goes to `/login` (page route exists, `app/main.py:51`) with `location.replace`. On failure it shows an error line and stays on the page. The shell's `title="Not wired yet"` is removed.

### `POST /api/v1/admin/login`
- **Purpose:** Admin sign-in. NOT itself gated by `/api/v1/admin/*` auth (chicken-and-egg) — explicitly exempt once the auth dependency lands (Security handoff, next step).
- **Request:** `{ "email": "string", "password": "string" }` (`email` validated as `EmailStr`).
- **Response (200 OK):** `{ "role": "SUPERADMIN" | "MANAGER" | "RECRUITER" }`. Also sets a `session_id` cookie: HttpOnly, SameSite=Lax, `Max-Age=28800` (8h), `Path=/`. **Secure flag dropped for now** (DECIDED 2026-10-30, user; see SECURITY.md section 2) because the app is LAN-only HTTP with no TLS.
- **Response (401):** `{"detail": "Invalid email or password."}` — identical generic message for an unknown email, a wrong password, and a deactivated account (`is_active=false`), to avoid user enumeration. A dummy bcrypt verify runs on an unknown email for timing parity with a real check.
- **Response (422):** malformed/missing `email` or `password`.
- **Response (429):** `{"detail": "Too many login attempts from this IP. Please try again later."}` — 5 failed attempts per IP per 60s, in-memory sliding window (`app/routers/auth.py`, `LOGIN_RATE_LIMIT_CACHE`), same pattern as the public apply endpoint's limiter but counting failures only.
- **Session mechanics:** on success, a `sessions` row is created (`id` = `secrets.token_urlsafe(32)`, `expires_at` = now + 8h fixed hard cap, `last_active_at` = now); `users.last_login_at` updated. `expires_at` never extends regardless of activity. NOT yet implemented: the `/admin/*` auth dependency that checks the cookie, enforces the 10-minute idle timeout against `last_active_at`, and updates it per request (existing gap, Security handoff, next step).
- **Status:** IMPLEMENTED this session (`app/routers/auth.py`, `login`). The 2026-10-30 additions to that page (password show/hide eye toggle, Remember me checkbox shell) are frontend only, no endpoint change, and Remember me never sends anything to this endpoint (see SECURITY.md section 2). `users`/`sessions` tables (migrations 014, 015) and ORM models applied and verified live earlier this session.

- **Timestamps (decided 2026-10-14, user):** Timestamps are stored in UTC (`timestamptz`, unchanged) and returned in Philippine Time (PHT, Asia/Manila, UTC+08:00) as ISO 8601 with the offset, e.g. `2026-10-14T11:16:23+08:00`. - **Rules:**
  * `YES_NO`: optional `options` of exactly 2 non-empty, distinct label texts (e.g. ["Own a car", "Do not own a car"]). `options[0]` is the display label for `YES`, `options[1]` for `NO`; omitted or null means the labels Yes / No. `answer_value` is always "YES" or "NO" and scoring is unchanged (implemented 2026-10-13 in POST and PATCH questions).
  * `MULTIPLE_CHOICE`: at least 3 `options` (no maximum), each trimmed, non-empty, and distinct (case-insensitive). On create, the server generates a stable `id` for each option; `answer_value` in `answer_points` is that `id`, never text or a letter. On PATCH, an option object that includes an existing `id` keeps that id (and can have its `text` edited); an option object with no `id` is treated as new and gets one assigned; an existing `id` left out of the submitted list is deleted along with any `answer_points` rows that reference it.
  * `OPEN_ENDED`: no `options`, no `answer_points`, `is_hard_requirement` must be false.
  * `is_required` (PROPOSED 2026-10-14, NOT implemented): optional boolean. Omitted means true for `YES_NO` and `MULTIPLE_CHOICE` and false for `OPEN_ENDED`. `is_hard_requirement` true requires `is_required` true (else 422). On apply, an unanswered optional YES_NO or MULTIPLE_CHOICE question is excluded from the score divisor and cannot fail the applicant.
  * `field_key` (RETIRED 2026-10-15: address, gender and date_of_birth are fixed apply fields, see `POST /api/v1/public/apply`; the text that follows is the old design and is NOT to be built): optional, one of `address`, `gender`, `date_of_birth`, allowed only on `OPEN_ENDED` (so no `options`, no `answer_points`, `is_hard_requirement` false). At most one question per `field_key` per form (409 if it already exists). It cannot be changed after create. A question with a `field_key` is never scored. Needs a migration for `job_questions.field_key` and `job_questions.is_required`, plus `applicants.address`, `applicants.gender` and `applicants.date_of_birth` (see SCHEMA.md).
  * `target_type` is `FAIL`, and every row needs a `job_id` of an existing job that uses this form (else 422). Pass/fail is set PER JOB (PROPOSED 2026-10-15, NOT implemented): the BRAND target, `brand_id` and `points` are dropped from the design (see SCHEMA.md). At most one row per answer and job (a duplicate returns 422).
  * One answer choice may have several rows, one per job it fails (for example fails Cashier but passes Store Supervisor).
  * `is_hard_requirement` true requires at least one FAIL row on the question (for at least one job). Hard requirements are non-negotiable: a FAIL on this question for a job fails that job outright and keeps it out of the suggested fit (decided 2026-10-15). In the Form Builder it is marked with a toggle next to Required: turning it on turns Required on and locks it, and it is offered only on YES_NO and MULTIPLE_CHOICE questions (PROPOSED 2026-10-15, NOT built).
  * `answer_points` is OPTIONAL for `YES_NO` and `MULTIPLE_CHOICE` (decided 2026-10-13): omitted or an empty list stores no rows, and `is_hard_requirement` is then false. This is how the Form Builder's first Save stores questions, before an answer-points editor exists.
  * Consequence (follows from the scoring rule in docs/SCHEMA.md): a question with no answer_points rows has no FAIL row on any choice, so every answer passes it. It never fails an applicant until FAIL rows are added with PATCH.
  * Storage: the row is created with `form_id` set and `job_id`, `parameter_id` and `expected_answer` NULL (columns relaxed by migration 004, applied 2026-10-13).
  * Interim limit (decided 2026-10-13): until the `answer_points` table exists, a non-empty `answer_points` list returns 422 ("answer points are not supported yet"), and `is_hard_requirement` true returns 422 (it needs a FAIL row). Both lift when the answer_points migration lands.
  * Validation: `question_text` is trimmed and must be non-empty. `question_type` must be one of the three values. Option labels are trimmed and must be non-empty. For `YES_NO`, `options` is omitted/null or exactly 2 labels (an empty list is 422), and the two labels must differ case-insensitively (UNVERIFIED assumption, matches the Form Builder). Stored `options` is null when omitted.
  * `display_order` is max + 1 for the form, so the first question gets 1 (verified live 2026-10-13).
  * Status: Implemented 2026-10-13 (`app/routers/admin.py`, `create_question`; schemas `QuestionCreateRequest` and `QuestionResponse` in `app/schemas.py`; migration 004). Verified live: 201 for YES_NO with default labels (`options` stored as SQL NULL, after the `none_as_null` fix on the model) and with custom labels, `display_order` 1 then 2; 422 for labels equal ignoring case, one label, blank text, unknown type, non-empty `answer_points`, `is_hard_requirement` true, MULTIPLE_CHOICE with 2 options, malformed form id; 404 unknown form id; 409 archived form. OPEN_ENDED create verified in the browser 2026-10-13 (Form Builder Save). NOT tested: MULTIPLE_CHOICE success path, an empty option label, an empty `options` list on YES_NO. Call site: `app/static/admin-sidebar.js` (Form Builder Save: creates the form, then posts each Yes / No card in order with its name and two labels as `options`; wired 2026-10-13; verified in the browser 2026-10-13: the form is created, then its Yes / No question is stored with its labels, confirmed in `job_questions`). NOT tested: the partial-failure path (form created but a question fails, then Save retried). Open ended cards are posted with `question_type` and `question_text` only, no `options` (Form Builder Save, wired and verified in the browser 2026-10-13: saved and reloaded in order). Other element types (Multiple Choice) block Save until they have contracts. No HR-auth check yet (existing gap; Security owns it). Known limit: `display_order` is max + 1 with no unique constraint, so two simultaneous saves to one form could share a number.
- **Response (201 Created):** the created question object (same shape as in form detail); `answer_points` is `[]` for now.
- **Errors:** 404 form not found; 409 the form is archived and read-only (same rule as rename, added 2026-10-13); 422 malformed `form_id`, rule violation, or one of the interim limits above.

### `PATCH /api/v1/admin/forms/{form_id}/questions/{question_id}`
- **Purpose:** Edit a question. `question_type` cannot be changed.
- **Request:** JSON, any subset of `question_text`, `options`, `is_hard_requirement`, `is_required` (PROPOSED 2026-10-14, NOT implemented; same rules as create, and setting it false on a hard-requirement question returns 422), `answer_points`. `field_key` cannot be changed. When `answer_points` is sent it REPLACES the question's whole set. The same rules apply.
- **Response (200 OK):** the updated question object.
- **Status:** Implemented 2026-10-13 (`app/routers/admin.py`, `update_question`). Same interim limit as create: non-empty `answer_points` or `is_hard_requirement: true` returns 422 (table doesn't exist yet). `question_type` is immutable (not in the request schema). Verified live: 200 question_text update and revert (on `zz save check 3`'s real question), 404 unknown question id. `options` on YES_NO (exactly 2 distinct labels) is implemented and verified in the browser 2026-10-13 (labels edited on an existing question persisted and reload correctly). The 422 paths for `options` are enforced in code but not exercised via direct API calls; the browser editor also blocks equal labels client-side. Call site: `app/static/admin-sidebar.js` (Form Builder, Edit on a loaded Yes / No card sends `question_text` and `options`; applies immediately, not on the modal's Save). ### Form submissions (no new endpoint)
A form's submissions are the applications for the jobs that use it: `GET /api/v1/admin/applications?form_id={form.id}` (section 2).

### Scoring and suggested fit (applies to `POST /api/v1/public/apply`)
- Answer values: `YES_NO` is "YES" or "NO", `MULTIPLE_CHOICE` is the chosen option's `id` (a string), `OPEN_ENDED` is the applicant's full free text, stored as is and never scored.
- Score: percent of scored questions (YES_NO and MULTIPLE_CHOICE) whose chosen answer has no FAIL row for the job applied to (job-level scoring, PROPOSED 2026-10-15, NOT implemented). OPEN_ENDED is excluded from the divisor, and so is (PROPOSED 2026-10-14, NOT implemented) any unanswered optional question. (The earlier field_key exclusion no longer applies: field_key is RETIRED as of 2026-10-15, see `POST /api/v1/public/apply`.) A hard-requirement question whose chosen answer has a FAIL row for the job applied to sets `has_hard_fail_flag` and status FAILED. The form's `pass_threshold` and `pooling_threshold` decide the status for every job that uses the form (PROPOSED 2026-10-15, NOT implemented; today the code reads the job's own thresholds).
- Suggested fit (PROPOSED 2026-10-15, replaces the brand-level fit, NOT implemented): at submit, the same answers are scored once for every other job that uses the same form and has at least one `answer_points` row. A job is stored as a fit only if its score is higher than the job applied to AND the answers hit no hard fail for it (a hard-requirement question whose chosen answer has a FAIL row for that job; hard-requirement questions are non-negotiable, decided 2026-10-15). A job the applicant hard-fails is never stored or shown as a fit. Each stored fit is an `application_fits` row (application, job, score), written in the same transaction as the application and never recomputed. The admin sees it as, for example, 76/100 on Store Supervisor and 80/100 on Operations Manager. The flag only informs: it never changes the score or status. Only jobs on the applicant's own form are compared. How the admin endpoints expose the fits (`GET /api/v1/admin/applications/{application_id}` and the job cards) is NOT decided yet and must be contracted before it is wired.
